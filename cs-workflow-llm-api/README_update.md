What can be meaningfully improved:
1. The regex extractor is a liability at scale. You've seen this firsthand today — every new prompt variation breaks something. The right fix is a small LLM extraction step (one claude-haiku call) for entity extraction only, keeping the workflow graph deterministic. The LLM handles language variation; the graph handles business logic. This is the standard production pattern.
2. No customer lookup by reference. Users say "customer 1001" meaning CUST-1001 but the API needs customer_id = 1. You need a /api/customers/lookup?ref=CUST-1001 endpoint and the workflow needs to call it before create_order. Without this, real CS agents can't use the system — they only know customer reference numbers, not DB PKs.
3. Conversation state is never truly reset between intents. The _STATE_BY_CONV in routes.py carries state across turns, which caused the "Please provide ship_to_address_id" bug we saw. When a new intent is detected in a continuing conversation, entities, errors, tool_results and actions_taken should be cleared while preserving only session-level context like bearer_token and tenant_id.
4. No human-in-the-loop escalation path. The policies.py and clarify_if_needed handle slot-filling, but there's no escalation node for cases that require supervisor approval — e.g. overnight shipping upgrades, large refunds, or repeated replacements. Your policy_rule table in the DB already has ALLOW_OVERNIGHT_FOR_REPLACEMENT and AUTO_REFUND_ALLOWED rules but nothing reads them at runtime.
5. The UI shows text answers but not enough structured data. The order card we just built is a good start, but for a real CS agent the UI needs: shipment tracking status, order timeline inline, address display with validation status, and action buttons (Cancel, Update Address) that pre-fill the chat with the right prompt. Right now the agent has to re-type everything.

8. No idempotency on order create. If the network hiccups and the user retries, you'll create duplicate orders. The idempotency_key table exists in your DB but nothing uses it. The workflow should generate and pass an idempotency key on every create_order call.
7. Token expiry is silent. When the Keycloak token expires mid-session, the user gets "Please provide ship_to_address_id" instead of "Your session has expired, please log in again." The routes.py should detect 401 errors from the orders API and surface a clear session-expired message.
8. No audit trail visible to the agent. tool_action_log and sales_order_event tables exist but the UI never shows them. A CS agent needs to see "what did this system do and when" — especially after a failed action.
9. Product catalog is too thin for realistic testing. Two products means most real-world prompts fail on data, not code. Adding 10-15 products and 5-6 customers with realistic refs would make the system actually testable end-to-end without constantly hitting data walls.
10. No graceful degradation when orders API is down. If cs-orders-api is unreachable, the workflow returns a generic error. It should detect network failures vs. business errors and respond differently — "Our order system is temporarily unavailable, please try again in a moment" vs. "Customer not found."
