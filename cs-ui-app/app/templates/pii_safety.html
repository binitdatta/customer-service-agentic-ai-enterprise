🔐 PII Safety & Data Protection

How the Customer Support Triage + Action Agent protects personally identifiable information (PII) across UI, APIs, Workflow Engine, and Keycloak.

PII Flow Boundaries

What Counts as PII in Our System?

  • Customer name
  • Email address
  • Phone number
  • Shipping / Billing address
  • Order history tied to identity
  • Payment metadata (never full card data)

Technical Safeguards

1️⃣ Least Privilege via Roles

Roles like order_read, order_write, replacement_create, and ticket_write restrict what agents and service accounts can access.

2️⃣ Audience-Restricted Tokens

Access tokens include audience claims like aud-cs-orders-api and aud-cs-workflow-api to prevent lateral movement.

3️⃣ PKCE + Public Client UI

The cs-ui client uses PKCE (S256) to prevent authorization code interception.

4️⃣ Service Account Isolation

Backend services use dedicated service accounts. No shared credentials. No UI token reuse.

AI-Specific PII Controls

  • 🔎 LLM receives only minimum required fields
  • 🧠 Sensitive values masked before prompt injection
  • 🚫 No raw database dumps into model context
  • 📜 Structured output enforcement (JSON schema)
  • 🧾 Human-in-the-loop for high-risk actions

Data Protection Layers

Layer Protection Mechanism
Transport TLS (HTTPS), HSTS headers
Identity OIDC + Keycloak token validation
Authorization Realm roles + client scopes
Application Field-level masking + DTO filtering
Logging No PII in logs; correlation IDs only
AI Layer Redaction before prompt + output validation

Compliance & Governance

Designed to align with:
  • GDPR – Data minimization & right to erasure
  • CCPA – Consumer access controls
  • FedRAMP-style logging discipline
  • Zero-trust security model
Security Principle

The Agent can only access what the token authorizes. The model can only see what the application exposes. Every action is policy-checked before execution.
