Why Structured Output

Reliability

“Structured output” means the model returns a machine-validated object (JSON) that matches a schema (JSON Schema / Pydantic). That object can drive:

Tool Calls
APIs: replace order, update address, open ticket
Workflows
LangGraph state transitions + guardrails
Tickets & Notes
Consistent payloads for CRM / ServiceNow
Analytics
Intent taxonomy, confidence, outcomes
In your Customer Support Triage + Action Agent, structured output is the bridge from: free-form complaint → validated intent → safe actions.
Anti-pattern to avoid
❌ Regex extraction from prose
order_id = re.search(r"#(\d+)", text)
Preferred pattern
✅ Schema + validation
{
  "intent": "DELIVERY_WRONG_ADDRESS",
  "order_id": "88421",
  "requested_action": "REPLACEMENT"
}

Core Patterns

Playbook

Intent + slots in one shot

Output a minimal JSON object capturing intent and required fields. Do not mix explanation with JSON. 

{
  "intent": "DELIVERY_ISSUE",
  "subtype": "WRONG_ADDRESS",
  "order_id": "88421",
  "requested_resolution": "REPLACEMENT",
  "shipping_speed": "OVERNIGHT"
}
Practical rule
If the object can’t be validated, treat it as “needs clarification” and ask exactly one question.

Clarify only what blocks action

Ask a single, targeted question—then re-run extraction with the answer.

Example clarifying question
“Can you confirm the correct shipping address for the replacement?”
Then validate again
{
  "confirmed_shipping_address": {
    "line1": "123 Main St",
    "city": "Naperville",
    "region": "IL",
    "postal_code": "60540",
    "country": "US"
  }
}

Plan with structured steps

Represent your plan as an array of steps so it’s auditable and easy to replay/idempotently execute. 

{
  "plan": [
    {"tool": "orders.get", "args": {"order_id": "88421"}},
    {"tool": "shipments.get_tracking", "args": {"order_id": "88421"}},
    {"tool": "orders.create_replacement", "args": {"order_id": "88421", "speed": "OVERNIGHT"}},
    {"tool": "tickets.create", "args": {"order_id": "88421", "category": "delivery_issue"}}
  ]
}
Never allow the model to “invent” tools. Validate tool names and args against a known registry.

Customer-ready narrative + structured receipt

Return a human explanation plus a “receipt” object for logs, dashboards, and traceability.

Customer message
“I’ve opened a delivery-issue ticket, created a replacement order, and requested overnight shipping (pending eligibility). Next, please confirm the correct address…”
Receipt JSON
{
  "case_id": "TCK-203991",
  "replacement_order_id": "R-77821",
  "policy": {"overnight_allowed": false, "reason": "outside_window"},
  "next_action": "confirm_address"
}

Schema Design

Strictness
Guidelines
  • Keep it small: only fields you’ll use.
  • Use enums for intent/action types.
  • Require critical fields (e.g., order_id).
  • Disallow extra fields to reduce drift.
  • Normalize: prefer nested objects for addresses, items, etc.
In practice: you’ll have multiple schemas: Triage, Action Plan, Ticket Draft, and Customer Reply.
Example: Triage Schema (concept)
{
  "type": "object",
  "additionalProperties": false,
  "required": ["intent", "order_id", "requested_resolution"],
  "properties": {
    "intent": { "type": "string", "enum": ["DELIVERY_ISSUE","BILLING_ISSUE","CANCELLATION","STATUS_QUERY"] },
    "order_id": { "type": "string", "pattern": "^[0-9]{4,12}$" },
    "requested_resolution": { "type": "string", "enum": ["REPLACEMENT","REFUND","REROUTE","INVESTIGATE"] },
    "shipping_speed": { "type": "string", "enum": ["STANDARD","EXPEDITED","OVERNIGHT"], "default": "STANDARD" },
    "notes": { "type": "string" }
  }
}
Pattern: additionalProperties=false + enums + regex patterns.

Code Examples

Flask + Python 

from enum import Enum
from pydantic import BaseModel, Field, ConfigDict

class Intent(str, Enum):
    DELIVERY_ISSUE = "DELIVERY_ISSUE"
    BILLING_ISSUE = "BILLING_ISSUE"
    CANCELLATION  = "CANCELLATION"
    STATUS_QUERY  = "STATUS_QUERY"

class Resolution(str, Enum):
    REPLACEMENT  = "REPLACEMENT"
    REFUND       = "REFUND"
    REROUTE      = "REROUTE"
    INVESTIGATE  = "INVESTIGATE"

class Triage(BaseModel):
    model_config = ConfigDict(extra="forbid")  # disallow unknown fields

    intent: Intent
    order_id: str = Field(pattern=r"^[0-9]{4,12}$")
    requested_resolution: Resolution
    shipping_speed: str = Field(default="STANDARD")
Why this works
  • Enums constrain intent/resolution to known values
  • Regex ensures sane order IDs
  • extra="forbid" prevents schema drift
  • Validation errors become “ask one clarifying question”

System:
You are a customer support triage engine.
Return ONLY valid JSON that matches the schema.
Do not include explanations, markdown, or extra keys.

User:
Text: "{{user_message}}"

Schema (JSON Schema):
{{triage_schema}}

Rules:
- If order_id is missing or ambiguous: set "needs_clarification" = true and
  set "clarifying_question" to ONE question.
- Otherwise set "needs_clarification" = false and leave "clarifying_question" empty.
Tip: include “Return ONLY JSON” in the system message and enforce parsing/validation server-side. 

# Pseudocode flow
triage = validate_or_clarify(model_json)

if triage.needs_clarification:
    return {"type": "question", "text": triage.clarifying_question}

facts = {

if not decision.allowed:

Treat structured output as input, not authority. Your policy engine is the final gate for refunds, overnight shipping, etc.

Guardrails & Policy Controls

Safety
Policy Gate
Centralize business rules (refund windows, overnight eligibility, replacement limits, fraud flags).
  • Allow / deny with reasons
  • Suggest safe alternatives
  • Log every decision
Idempotency
Make tool calls replay-safe: repeated requests shouldn’t create duplicate replacements or tickets.
  • Idempotency keys per case
  • Dedup on order_id + issue_type
  • Store execution receipts
Auditability
Structured output makes audits easier when you capture schema version, inputs, and outcomes.
  • Correlation IDs end-to-end
  • Store request + validated JSON
  • Store policy decisions + tool results

Common Failure Modes

Pitfalls
1) Overly large schema
The model “fills” optional fields with invented values.
Fix Use minimal required fields, forbid extras.
2) Mixed prose + JSON
Parser fails; you end up writing cleanup code.
Fix “Return ONLY JSON” + strict parsing.
3) Tool hallucination
Model references tools you don’t have.
Fix Validate tool names against registry.
4) No policy gate
Model “approves” refunds/overnight shipping improperly.
Fix Policy engine is the final authority.
