State & Memory in Agentic Systems

How an agent remembers context, tracks steps, enforces safety, and stays consistent across multi-turn workflows.

Concepts Patterns Order Triage Mapping Guardrails Anti-Patterns
Bootstrap 5 LangGraph-friendly Production mindset

State

The current working context: what we know, what we’ve decided, what step we’re on, and what’s still missing.

Memory

The stored knowledge across turns/sessions: customer preferences, prior tickets, policy decisions, and conversation history.

Persistence

Where state/memory lives: session, cache, DB, or an external store. Defines reliability, privacy, and replayability.

Core Concepts

Foundations

What “State” usually contains

  • Intent + classification (delivery issue, refund request, address change)
  • Entities (order_id, customer_id, item_sku, carrier, tracking_id)
  • Facts fetched via tools (order status, address on file, delivery proof, inventory availability)
  • Workflow step (triage → verify → policy check → action → confirm)
  • Open questions (missing address confirmation, “overnight allowed?”)
  • Safety flags (refund requires approval, suspicious pattern, high-risk change)

What “Memory” usually contains

  • Conversation history (short-term memory)
  • User profile preferences (delivery instructions, default address, contact preference)
  • Prior outcomes (previous replacements/refunds, known fraud signals)
  • Policy knowledge (what shipping upgrades are allowed)
  • Operational context (recent carrier delays, outage notices)
Ephemeral State
Lives only during one request/turn. Fast, cheap, but not recoverable after restart.
Session State
Lives across browser session/login. Useful for UI experiences and short workflows.
Durable Memory
Stored in DB/cache/vector store. Enables continuity, auditing, and “resume after failure”.

Practical Design Patterns

Architectural

Define a stable schema for state (like a DTO). Every node reads/writes the same structured object. This reduces drift and makes your graph debuggable.

Example state fields (conceptual)
  • intent, order_id, customer_id
  • facts: order_status, delivery_address, tracking_status, item_availability
  • policy: allowed_actions, requires_human_approval
  • actions_taken: replacement_created, ticket_opened
  • pending_question: “Confirm correct shipping address?”

Keep short-term context in conversation/state. Persist only what you truly need long-term (auditable outcomes, preferences, stable facts).

Short-Term (per conversation)
  • Current issue summary
  • Latest tool results
  • Clarifying question and answer
  • Step pointer (where we are in the flow)
Long-Term (durable)
  • Replacement/refund decisions
  • Ticket IDs and timestamps
  • Fraud/abuse flags (with governance)
  • User preferences (opt-in)

Persist key transitions (inputs, tool calls, decisions, outputs). If the process crashes, you can resume deterministically and produce an audit trail.

Tip: Log correlation IDs end-to-end (UI → workflow API → orders API → ticketing) so every action is traceable.

Mapping to Your Order Support Triage + Action Agent

Use Case

Example customer message

User
“My order #88421 was delivered to the wrong address. I want a replacement shipped overnight.”

State progression (high-level)

  1. Classify: delivery issue + replacement request + expedited shipping request
  2. Fetch facts: order details, delivery proof, address, tracking, item availability
  3. Policy check: eligible for replacement? overnight allowed?
  4. Clarify (only if needed): confirm correct address, confirm recipient name
  5. Act: create replacement, open ticket, notify customer
  6. Close: summary + next steps + SLA

What to persist vs not persist

Persist (Durable)
  • ticket_id, replacement_order_id
  • policy decision + reason
  • final resolved address (if approved)
  • timestamps + correlation_id
Don’t persist (unless required)
  • raw chat transcript (or store with strict retention)
  • full PII details beyond need
  • intermediate tool responses that contain sensitive fields

Guardrails: Safety, Policy, and Authorization

Must-have

Policy Gate

Don’t refund/overnight/replace unless policy says yes. Store policy decisions in state as structured fields (allowed_actions, requires_approval).

Tool Authorization

Gate “write” tools behind scopes/roles. Your agent’s state should carry who is acting and what they are allowed to do.

Audit + Correlation

Every action taken must be traceable: correlation ID, tool input/output summaries (sanitized), and outcome IDs (ticket/replacement).

Rule of thumb: The model may “decide”, but your code enforces “allow/deny”. State should record why a decision was allowed/blocked.

Common Anti-Patterns

Avoid
“Everything is memory”
Persisting raw transcripts + PII everywhere increases risk and makes compliance painful. Persist outcomes and minimal required facts.
Unbounded state growth
Tool outputs accumulate forever; prompts blow up; costs rise; latency increases. Summarize and prune.
Hidden decisions
If the agent decides “overnight shipping” without recording policy checks, you can’t audit or debug.
No idempotency
Retries create multiple replacements/tickets. Record action IDs in state and make tool calls idempotent.
