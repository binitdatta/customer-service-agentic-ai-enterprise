Observability Architecture

End-to-end visibility for the Customer Support Triage + Action Agent. Covers Logs, Metrics, Distributed Tracing, Security Auditing, and AI Decision Transparency.

Why Observability is Critical for Agentic AI

  • Diagnose failed replacement orders or policy denials
  • Trace multi-step agent decisions (classify → fetch → act)
  • Audit who executed privileged operations
  • Detect token misuse or role escalation
  • Measure SLA and latency across APIs

End-to-End Telemetry Flow

Observability Layers

🔹 Structured Logging
  • Correlation ID per request
  • Order ID tagging (#88421)
  • Agent step logging (classify, fetch, act)
  • Masked PII fields
📊 Metrics
  • API latency (P95, P99)
  • Replacement creation rate
  • Policy denial frequency
  • Error rate by endpoint
🧵 Distributed Tracing
  • Trace ID propagated via headers
  • UI → Orders API → Workflow API
  • DB query span timing
  • External API spans
🔐 Security & IAM Events
  • Role-based access enforcement
  • Service account token usage
  • Admin actions auditing
  • Authentication failures

Identity & Token Observability

Realm: cs-triage

  • Track access tokens issued for cs-ui
  • Audit service accounts: cs-orders-api, cs-workflow-api
  • Monitor role usage (order_write, replacement_create, ticket_write)
  • Track admin operations via realm-management roles
Security events and token issuance must be forwarded to centralized logging (SIEM).

AI Agent Decision Transparency

  • Log classification output (intent: delivery_issue)
  • Log policy decision (overnight shipping allowed = true/false)
  • Log tool calls executed
  • Log clarifying question (if any)
  • Log final action summary

Recommended Observability Stack

ELK / OpenSearch / Cloud Logging

Metrics

Prometheus + Grafana

Tracing
