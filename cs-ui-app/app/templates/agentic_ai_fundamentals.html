What is Agentic AI?

Concept

Agentic AI is an approach where an LLM is used as a controller that can: interpret user goals, maintain state, call tools, verify results, and take actions under guardrails.

Chatbot
  • Answers questions
  • Mostly stateless
  • No real actions
  • Low audit requirements
Agent
  • Completes tasks end-to-end
  • Stateful workflows
  • Calls tools / APIs
  • Policy + audit-friendly
Agents must be constrained by policy. “Autonomous” is never a license to refund, reorder, or escalate without rules.
Building Blocks
Planner / Router
Decides which path to take (triage, research, action)
State / Memory
Carries user context, tool results, and decisions
Tools
Order lookup, address validation, replacement creation, ticketing
Guardrails
Policies, human approvals, and fail-safe behavior
Observability
Correlation IDs, traces, audit logs, structured events

Core Capabilities

Skills
Classification

Convert unstructured text into structured intent, entities, and priority: “delivery issue + replacement + overnight request”.

Fact Retrieval

Pull authoritative facts from tools/DBs: order status, tracking, address, inventory availability.

Clarification

Ask one high-value question when ambiguity blocks safe action: “Confirm the correct delivery address?”.

Action Execution

Execute tool actions under policy constraints: create replacement, shipping upgrade, open ticket.

Reference Architecture

Blueprint

A minimal enterprise-grade design separates the agent brain from tools, and enforces policy checks before any irreversible actions. 

User → UI (Flask) → Agent Orchestrator (LangGraph)
                     ↓
              Policy Engine (rules)
                     ↓
  Tools: Orders API | Address Resolve | Inventory | Ticketing | Shipping/Carrier
                     ↓
           Audit Logs + Tracing + Metrics
Security
OIDC login (Keycloak), token relay to APIs, per-tool scopes, least privilege.
Auditability
Structured events per step: intent → tools → decisions → actions → response.
Agent Layers

Classify request type, extract order number, urgency, requested action, and confidence.

Fetch authoritative facts from services. Prefer idempotent reads before writes.

Validate refunds/replacements, shipping upgrades, and eligibility rules. Require approval if thresholds are exceeded.

Execute safe writes with idempotency keys, then generate a customer-ready response.
Design note: keep your “policy engine” separable from prompts so you can change rules without retraining or prompt surgery.

Lifecycle: From Message to Outcome

Flow
1) Understand
Parse intent, entities, constraints, sentiment/urgency.
2) Retrieve
Call tools to collect facts (read-first).
3) Decide
Apply rules, ask 1 clarifying question if blocked.
4) Act
Execute idempotent actions + produce customer-ready reply.

Guardrails & Safety Controls

Required
Policy Enforcement
  • Never refund/overnight ship unless policy permits
  • Require approval above thresholds (cost, VIP rules, fraud signals)
  • Validate eligibility: delivery proof, time window, item availability
  • Use “deny by default” for high-risk actions
Audit & Observability
  • Correlation ID per request (end-to-end tracing)
  • Log every tool call: inputs (redacted), outputs, latency, errors
  • Structured “decision events”: why action taken/blocked
  • Replayable workflow state for debugging

Implementation Patterns

Practical
Router Pattern

Use a classifier to route to a sub-graph: delivery issue, billing, returns.

Read-Then-Write

Always retrieve facts before writing. Prefer idempotent actions with retry semantics.

Idempotency Keys

Prevent duplicate replacements/refunds by using a deterministic request key for writes.

Example: Customer Support Triage + Action Agent

End-to-End
User Message

“My order #88421 was delivered to the wrong address. I want a replacement shipped overnight.”

Agent Steps
  1. Classify: delivery issue + replacement + shipping upgrade request
  2. Retrieve: order, tracking, delivery confirmation, inventory
  3. Clarify if needed: confirm correct shipping address
  4. Policy gate: check eligibility & shipping upgrade rules
  5. Execute: create replacement + open ticket
  6. Respond: what we did + what happens next
Structured Output (Example)
{
  "intent": "DELIVERY_ISSUE_REPLACEMENT",
  "order_id": "88421",
  "requested_shipping": "OVERNIGHT",
  "needs_clarification": true,
  "clarifying_question": "Can you confirm the correct shipping address for the replacement?",
  "actions": [
    {"tool": "orders.get", "status": "success"},
    {"tool": "inventory.check", "status": "success"},
    {"tool": "policy.evaluate", "status": "success"},
    {"tool": "ticket.create", "status": "planned"},
    {"tool": "replacement.create", "status": "planned"}
  ]
}
This is the contract between the model and your backend: structured intent + tool plan + policy status.
