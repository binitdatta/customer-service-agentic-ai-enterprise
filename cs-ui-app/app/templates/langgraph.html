What is LangGraph, in plain terms?

LangGraph is a state machine for LLM apps. You define: state (what the agent knows), nodes (steps), and edges (how to move between steps).

A “chatbot” becomes a workflow: deterministic where it must be, flexible where it can be.
Core primitives
  • State: typed object holding order_id, customer, policy decisions, tool results
  • Nodes: LLM steps, tool calls, validators, routers, human approvals
  • Edges: unconditional transitions or conditional routing (if/else)
  • Memory: persist state across turns or sessions when needed

Best fit: multi-step flows like support triage, claims, onboarding, approvals, and any “think → verify → act” automation.

A simple agent loop repeatedly prompts the model and hopes it “does the right thing.” LangGraph lets you explicitly model steps like: classify → fetch → validate → act → confirm → respond, with deterministic routing and typed state.

You can enforce: “No refund or overnight upgrade unless policy permits,” and route to a clarifying question node only when critical data is missing. Tool calls happen behind a strict policy gate node.

Reference Architecture

  1. UI (Flask/Bootstrap): chat + transcripts + run IDs
  2. LangGraph Orchestrator: graph definition + routing + state
  3. Tools Layer: Orders API, Inventory API, Ticketing, Notifications
  4. Policy Engine: shipping/refund rules, entitlements, limits
  5. Observability: correlation-id, structured logs, traces
  6. Persistence: run store, state snapshots, audit trail
Treat every tool call as a transactional action with an audit record.

Guardrail patterns

Policy Gate Node
Centralize entitlement checks before any state-changing tool call (refund, replace, expedite).
Human-in-the-loop Approval
Route “high impact” actions to a manager approval node (overnight shipping, refunds above threshold).
Idempotent Tools
Use idempotency keys per run_id to avoid double replacement or double refund.
Typed State + Validation
Validate extracted fields (order_id format, address completeness) before hitting downstream APIs.
Never let the model directly “decide” refunds/expedite. Make it propose, then enforce via policy.
